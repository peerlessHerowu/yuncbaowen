### 2.3 dedup-checker.ts

职责：检测改写结果中残留的连续词 + 自动修补

```typescript
export interface ConsecutiveMatch {
  fragment: string        // 匹配到的文字片段
  originalPos: number     // 在原文中的位置
  rewrittenPos: number    // 在改写文中的位置
  length: number          // 片段长度
}

/**
 * 检测改写文本中与原文连续 N 字以上相同的片段
 * 算法：滑动窗口，O(n*m) 但可接受（5000字 < 200ms）
 */
export function detectConsecutiveMatches(
  original: string,
  rewritten: string,
  threshold: number = 8
): ConsecutiveMatch[]

/**
 * 计算预估相似度（0-100%）
 * 基于匹配片段覆盖率 + 长片段加权
 */
export function estimateSimilarity(
  original: string,
  rewritten: string,
  matches: ConsecutiveMatch[]
): number

/**
 * 对残留片段做局部改写修补
 * 返回修补后的完整文本
 */
export async function fixMatches(
  original: string,
  rewritten: string,
  matches: ConsecutiveMatch[],
  userId: number,
  maxFixes?: number  // 默认 10
): Promise<{ fixed: string; fixCount: number }>
```

#### 连续词检测算法优化

朴素实现 O(n*m*k) 太慢，优化方案：

```
1. 预处理：对原文建立 suffix array 或 n-gram 索引
2. 检测：从 threshold 开始，用原文的 n-gram 在改写文中做 indexOf
3. 合并：相邻/重叠的匹配合并为最长匹配
4. 过滤：去掉专有名词匹配（不算重复）
```

实际实现中选择「n-gram 索引」方案（空间换时间）：
- 对原文按 threshold 长度生成所有 n-gram，存入 Set
- 对改写文按相同长度滑动，检查是否在 Set 中
- 时间复杂度 O(n+m)，5000 字文章 < 50ms

**前端处理逻辑**：
- `stage` 事件：更新进度条和阶段文字

- `done` 事件：标记完成，显示最终相似度
- 修补阶段的 `chunk`：替换整个输出区域内容（不是追加）

## 四、性能设计

### 4.1 时间预算分配

| 阶段 | 预算 | 说明 |
|------|------|------|
| Layer 0 预处理 | < 50ms | 纯 CPU，分段 + 提取关键词 |
| Layer 1 AI 改写 | 10-18s | LLM 流式输出，2000 字约 12s |
| Layer 2 连续词检测 | < 100ms | n-gram 索引法 |
| Layer 3 修补 | 0-5s | 视残留数量，通常 0-3 处 |
| Layer 4 Randomizer | < 50ms | 纯 CPU 字符串操作 |
| Layer 5 相似度计算 | < 20ms | 复用 Layer 2 结果 |
| **总计** | **< 25s** | |

### 4.2 长文分段并行

当原文 > 4000 字时：
- 分为 2-3 段
- 各段**串行**处理（因为共享 token budget）
- 每段完成立即流式输出给前端
- 前端看到的是连续的文字流

> 注意：不做并行 LLM 调用，因为 Kiro Gateway 的 rate limit 和我们的 token 预算。

### 4.3 内存管理

- 原文和改写文同时存在于内存：最大 24KB（12000 字 × 2）
- n-gram 索引：最大 ~50KB（5000 个 8-gram）
- 可接受，无需特殊优化

## 五、安全设计

### 5.1 输入验证

| 检查项 | 规则 | 错误码 |
|--------|------|--------|
| 原文长度 | 30 ≤ length ≤ 12000 | 400 |
| intensity | 枚举值 | 400 |
| intent | 枚举值或 undefined | 400 |
| keywords | 长度 ≤ 200 | 400 |
| 用户认证 | 必须登录 | 401 |
| 频率限制 | 120次/分钟（已有） | 429 |

### 5.2 Prompt 注入防护

- 用户输入的 `original` 放在 prompt 最末尾
- system prompt 中明确指令优先级
- 不允许原文内容覆盖 system 指令

### 5.3 敏感内容

- 不做内容审核（用户自行负责）
- 不持久化原文（只存改写结果到 creations 表）

## 七、错误处理

| 场景 | 处理方式 |
|------|---------|
| LLM 调用失败 | 已有 fallback 机制（多 provider 切换） |
| 修补后仍有残留 | 告警但不阻塞，前端标注「建议手动调整」 |
| 分段拼接后语义断裂 | 兜底：拼接后做一次通顺性 prompt 检查 |
| 流式输出中断 | 前端 abort + 已输出内容保留 |
| 超时（>60s） | SSE 发送 timeout 事件，前端展示已有内容 |
