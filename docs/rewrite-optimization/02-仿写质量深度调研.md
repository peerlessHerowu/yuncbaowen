# 仿写效果深度调研报告

> 日期：2026-08-18
> 测试链接：https://m.toutiao.com/article/7674831042393506354/
> 问题背景：改写后文皮皮检测相似度仍然偏高，且截图显示改写结果里有大量图片 URL 堆叠

---

## 一、问题分层诊断

### 1.1 实测数据

通过 node 脚本直接验证 `detectConsecutiveMatches` 算法行为：

| 场景 | 匹配数 | 相似度 |
|------|------|------|
| 含图片 markdown 的原文 vs 改写文 | 2 | **100%** |
| 去除图片 markdown 后的纯文字 | 0 | **0%** |

**文字改写质量其实没问题，是图片 markdown 污染了相似度计算。**

### 1.2 根因分解

**问题一（最严重）：相似度计算没有排除图片 markdown**

图片 markdown 格式：`![图片标题](超长URL)`

- 头条文章每张图片有相同的 alt text（文章标题），如「郭富城娇妻路人照被疯传！网友：方媛原来长这样，照妖镜都没这真」（31字）
- 7 张图片 × 31 字标题 = 217 字的相同文字，占文章总字符的 ~30%
- 加上 URL 本身（每条约 150 字符），图片 markdown 占原文 **40-80%** 的字符数
- 连续词检测把这些全部算作"匹配"，导致相似度虚高到 40-85%

**问题二（重要）：图片 URL 送给 LLM 产生干扰**

每张图片的 URL 带有以下特殊内容：
```
https://p11-sign.toutiaoimg.com/tos-cn-i-xxx/{hash}~tplv-tt-large.image
  ?_iz=30575&lk3s=06827d14&x-expires=1787668886&x-signature=Q1crqhS39...
```

- URL 总长度约 200+ 字符
- 包含 `%2B`、`%2F`、`%3D` 等 URL 编码字符
- `x-expires` 参数：URL 有过期时间，几个小时后图片将无法访问（对用户来说是死链）
- 7 张图片 URL ≈ 1400+ 字符额外 token 消耗
- LLM 被要求"保留图片标记"，但超长的特殊字符序列容易导致输出截断或乱码

**问题三（重要）：图片 alt 文字重复**

同一篇文章里 7 张图片都用了相同的文章标题作为 alt，这不是正确的 alt text。LLM 在改写时保留了这 7 个相同的长标题，这不仅影响查重检测，也让阅读体验很差。

**问题四（中等）：相似度计算本身的算法问题**

`estimateSimilarity` 函数在计算时：
- 用"去空白"后的原文总字数作为分母
- 但图片 markdown 里的 URL 字符（英文、数字、特殊符号）也被包含在"去空白"后的字符数里
- 导致：图片 URL 长度越大，相似度越高（即使文字本身改写得很好）

**问题五（轻微）：fix 的上限太低**

`fixConsecutiveMatches` 默认 `maxFixes=8`（后来改成了 `Math.min(matches.length, 15)`），但图片导致的"假匹配"会消耗修补次数，让真正需要修补的文字片段得不到处理。

## 二、多角度优化方案

### 2.1 修复一：改写前提取图片、改写后插回（最关键）

**核心思路**：把图片从原文中"摘除"再送给 LLM，改写完后再把图片插回对应段落位置。

```
原文（含图片）
  ↓ preprocess()
纯文本（不含图片） + 图片位置映射表
  ↓ LLM 改写
改写后纯文本
  ↓ reinsertImages()
改写后文本 + 图片（恢复到对应段落）
```

**图片位置映射**：用段落索引记录每张图片在第几段后：

```typescript
interface ImagePosition {
  afterParagraphIndex: number  // 在第 N 段后面
  markdown: string             // 完整的 ![alt](url)
}

function extractImages(content: string): {
  textOnly: string
  images: ImagePosition[]
} {
  const paragraphs = content.split(/\n\n+/)
  const images: ImagePosition[] = []
  const textParagraphs: string[] = []

  paragraphs.forEach((para, idx) => {
    // 图片单独成段（头条的格式）
    if (/^!\[/.test(para.trim())) {
      images.push({ afterParagraphIndex: textParagraphs.length - 1, markdown: para.trim() })
    } else {
      textParagraphs.push(para)
    }
  })

  return { textOnly: textParagraphs.join('\n\n'), images }
}

function reinsertImages(rewrittenText: string, images: ImagePosition[]): string {
  const paragraphs = rewrittenText.split(/\n\n+/)

  // 从后往前插入，避免位置偏移
  const sortedImages = [...images].sort((a, b) => b.afterParagraphIndex - a.afterParagraphIndex)

  sortedImages.forEach(img => {
    const pos = Math.min(img.afterParagraphIndex, paragraphs.length - 1)
    paragraphs.splice(pos + 1, 0, img.markdown)
  })

  return paragraphs.join('\n\n')
}
```

**效果**：
- LLM 只需处理纯文字，token 消耗减少 40-80%
- 改写质量大幅提升（没有 URL 干扰）
- 图片自动插回到改写后对应段落

### 2.2 修复二：相似度计算排除图片 markdown

在 `detectConsecutiveMatches` 和 `estimateSimilarity` 计算前，先去掉图片 markdown：

```typescript
const IMG_RE = /!\[[^\]]*\]\([^)]*\)/g

export function detectConsecutiveMatchesText(
  original: string,
  rewritten: string,
  threshold: number = 8
): ConsecutiveMatch[] {
  // 计算时排除图片 markdown
  return detectConsecutiveMatches(
    original.replace(IMG_RE, ''),
    rewritten.replace(IMG_RE, ''),
    threshold
  )
}
```

### 2.3 修复三：URL 过期问题 — 图片代理缓存

头条图片 URL 有 `x-expires` 参数，几小时后签名过期变成死链。

**方案**：抓取时立即下载图片，保存到本地/OSS，替换为永久 URL：

```typescript
async function cacheImage(url: string): Promise<string> {
  // 1. 下载图片
  const resp = await fetch(url, { headers: { Referer: 'https://m.toutiao.com/' } })
  const buffer = await resp.arrayBuffer()

  // 2. 计算 hash（防重复存储）
  const hash = createHash('md5').update(Buffer.from(buffer)).digest('hex').slice(0, 16)
  const ext = url.includes('.png') ? 'png' : 'jpg'
  const filename = `${hash}.${ext}`

  // 3. 保存到本地 uploads 目录（或 OSS）
  const localPath = path.join(UPLOAD_DIR, 'cached-images', filename)
  await fs.writeFile(localPath, Buffer.from(buffer))

  // 4. 返回永久 URL
  return `/uploads/cached-images/${filename}`
}
```

**效果**：
- 图片永久可访问，不会过期
- 不依赖第三方服务器
- 可顺便去水印（结合第六节的水印处理方案）

### 2.4 修复四：图片 alt text 优化

头条图片都用文章标题作为 alt，同一篇文章 7 张图 alt 完全相同。

可以在抓取时自动生成有意义的 alt text：
- 第一张图：保留标题
- 后续图：「配图 2」「配图 3」...
- 或者用 AI 简短描述（调用 vision API）

```typescript
// 在 parseToutiao 的 htmlToTextWithImages 中
let imgCount = 0
html.replace(/<img[^>]+>/gi, (imgTag) => {
  imgCount++
  const altText = imgCount === 1 ? (alt?.[1] || '图片') : `配图${imgCount}`
  return `\n![${altText}](${url})\n`
})
```

### 2.5 优化五：prompt 增加"忽略图片标记"指令

即使做了图片提取（2.1），用户也可能直接粘贴含图片的文章。在 prompt 里明确指令：

```
在改写时：
- 遇到 ![xxx](url) 格式的图片标记，直接原样保留，不要改动任何内容
- 图片前后的文字正常改写
- 不要把图片URL当作文字内容来处理
```

### 2.6 优化六：改写前内容质量评估

在送 LLM 之前，先评估内容质量，决定改写策略：

```typescript
interface ContentAnalysis {
  pureTextRatio: number    // 纯文字占比（排除图片）
  avgSentenceLen: number   // 平均句长
  imageCount: number       // 图片数量
  isHighQuality: boolean   // 是否适合直接改写
}

function analyzeContent(text: string): ContentAnalysis {
  const withoutImages = text.replace(/!\[[^\]]*\]\([^)]*\)/g, '')
  const totalChars = text.replace(/\s+/g, '').length
  const textChars = withoutImages.replace(/\s+/g, '').length
  const sentences = withoutImages.split(/[。！？!?]+/).filter(s => s.trim().length > 5)
  const avgLen = sentences.reduce((s, x) => s + x.length, 0) / Math.max(sentences.length, 1)
  const imgCount = (text.match(/!\[/g) || []).length

  return {
    pureTextRatio: textChars / Math.max(totalChars, 1),
    avgSentenceLen: avgLen,
    imageCount: imgCount,
    isHighQuality: textChars > 300 && avgLen > 15,
  }
}
```

如果 `pureTextRatio < 0.3`（图片占比超过 70%），说明这是一篇以图片为主的文章，改写效果会很差，应该提示用户。

## 三、改写质量的其他瓶颈

### 3.1 图片以外的相似度来源

除了图片 markdown，还有以下内容会造成真实相似度偏高：

| 原因 | 说明 | 解法 |
|------|------|------|
| 专有名词 | 人名、品牌、地名无法改 | 正确，这类不计入相似度 |
| 数字和日期 | 「39岁」「三个孩子」必须保留 | 正确，不算抄袭 |
| 固定短语 | 公众号固定格式「声明：本文内容...」 | 在送 LLM 前过滤掉声明/版权行 |
| 句式骨架保留 | LLM 只换了词没换句式 | prompt 加强：明确要求句式重构 |
| 段落顺序一致 | 改写文和原文段落顺序完全一样 | prompt 加入逻辑重排要求 |

### 3.2 LLM 的懒惰倾向

实测发现，即使 prompt 明确要求「逻辑重排」，LLM 在处理原文时经常：
- 按原文顺序逐段改写，只换词不换顺序
- 遇到短段落时直接保留原句
- 对名人/热点内容过于谨慎，不敢大幅改动

**解法**：在 prompt 里加入强制性的结构约束，而不是建议性的要求。

```
❌ 建议性：「可以适当调整段落顺序」
✅ 强制性：「第一段必须和原文最后一段内容相关，不能以相同主题开头」
```

### 3.3 温度参数的影响

当前 `temperature=0.7`，但对于降重任务：
- 低温度（0.3-0.5）：更保守，倾向于保留原文句式
- 中温度（0.7）：平衡，但 LLM 仍倾向于"小改"而非"大改"
- 高温度（0.9-1.0）：更有创意，但可能偏离原意

实验表明：降重任务用 **0.8-0.9** 效果更好，配合强约束 prompt 才能既有创意又不跑偏。

## 四、实施优先级

### P0（立即修复，影响最大）

**1. 相似度计算排除图片 markdown**

修改 `dedup-checker.ts` 的 `detectConsecutiveMatches` 和 `estimateSimilarity` 调用处，在计算前 strip 掉 `![...](...)` 内容。

代码量极小，1 小时内完成，直接让相似度从虚高的 40-85% 恢复到真实值。

**2. 改写前提取图片，改写后插回**

修改 `rewrite-pipeline.ts` 的 Layer 0 预处理，调用 `extractImages()` 把图片摘出来，Layer 4 之后调用 `reinsertImages()` 插回。

这个修复让 LLM 专注于文字改写，token 消耗降低 40-80%，改写质量显著提升。

### P1（近期，1-2天）

**3. 图片 URL 过期修复：下载缓存为永久链接**

在 `fetchArticle` 返回结果后，对所有图片 URL 进行异步下载并替换为本地路径。结合水印处理一起做，一石二鸟。

**4. 图片 alt text 去重**

`htmlToTextWithImages` 中对重复 alt 的图片自动编号（「配图2」「配图3」），避免同一文章 7 张图都有相同的 31 字标题。

**5. 改写前过滤版权声明行**

头条文章开头常有「声明：本文内容均是本人原创，请勿搬运抄袭」这类固定格式，这些是"样板文"，不需要改写，也不应计入相似度。在预处理阶段过滤掉。

### P2（后续优化）

**6. temperature 调整为 0.85**

降重场景从 0.7 调高到 0.85，配合现有的强约束 prompt，让 LLM 改写更大胆。

**7. prompt 加入强制结构约束**

把「适当调整顺序」改为「第一段必须和原文最后一段内容相关」这类强制约束，消除 LLM 的懒惰倾向。

**8. 内容质量预评估**

改写前检测 `pureTextRatio`，如果文字占比 < 30%（以图片为主），提示用户「该文章以图片为主，文字改写效果有限」。

## 五、总结

### 根因汇总

| 问题 | 严重程度 | 修复难度 | 预期收益 |
|------|---------|---------|---------|
| 相似度计算未排除图片 | P0（影响所有含图文章） | 低 | 相似度从虚高 80% 恢复真实值 |
| 图片 URL 送入 LLM | P0 | 低-中 | token 减少 40-80%，改写质量提升 |
| 图片 URL 过期 | P1 | 中 | 图片永久可访问 |
| 图片 alt 重复 | P1 | 低 | 降低真实相似度 10-20% |
| 版权声明未过滤 | P1 | 低 | 去除无意义改写内容 |
| temperature 偏低 | P2 | 极低 | 改写更有创意 |

### 关键洞见

最核心的问题不是 prompt 设计，而是**数据预处理不完整**：
1. 图片不应该和文字一起送给 LLM
2. 相似度不应该把图片 markdown 计入

这两个修复成本很低，但效果会非常显著。把这两个改了之后，再看看实际相似度，再决定是否需要进一步调整 prompt 策略。
