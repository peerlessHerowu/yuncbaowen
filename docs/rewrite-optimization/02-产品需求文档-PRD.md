# 二次仿写降重 - 产品需求文档（PRD）

> 版本：v2.0 | 日期：2026-08-16
> 状态：评审中

---

## 一、背景与目标

### 1.1 痛点

当前「二次仿写」功能对用户提交的原文进行 AI 改写后，在文皮皮等查重平台检测相似度仍高达 21.29%（判定为抄袭）。用户使用降重功能的核心诉求是「过查重」，当前产品无法满足。

### 1.2 目标

| 指标 | 当前 | 目标 | 衡量方式 |
|------|------|------|---------|
| 文皮皮相似度 | 21.29% | < 5% | 实测 5 篇文章取平均 |
| 改写后可读性 | 一般 | 流畅自然 | 人工评分 ≥ 8/10 |
| 改写耗时（2000字） | ~15s | < 25s（含后处理） | 端到端计时 |
| 用户操作步数 | 3步 | 3步（不增加） | 粘贴→选参数→点击 |

### 1.3 非目标

- 不做学术论文专用降重（我们的定位是公众号/自媒体文章）
- 不提供实时查重 API 对接（成本过高）
- 不做多语言翻译降重

## 二、用户画像与场景

### 2.1 核心用户

| 用户类型 | 典型场景 | 核心诉求 |
|---------|---------|---------|
| 自媒体编辑 | 参考竞品爆文改写发布 | 过平台原创检测，不被判为洗稿 |
| 公众号运营 | 将旧文/素材改写为新内容 | 降重率 < 5%，保持信息完整 |
| 大学生 | 课程论文/报告降重 | 过知网查重，保留核心论点 |
| 内容创业者 | 批量改写素材库内容 | 高效出稿，单篇 < 30s |

### 2.2 核心使用场景

**场景 A：降重（最高频）**
```
用户流程：
1. 粘贴一篇别人的/自己旧的文章（或公众号链接）
2. 选择「降重避重」意图 + 「中度/深度」改写强度
3. 点击「开始仿写」
4. 等待 15-25s，看到改写结果逐字流式输出
5. 结果面板顶部显示「预估相似度：3.2%」
6. 点击「复制」→ 粘贴到自己的发布平台
```

**场景 B：深度改写（信息重组）**
```
用户流程：
1. 粘贴原文
2. 选择「深度改写」强度（触发 L3 信息重组模式）
3. 系统先提取核心要点，展示给用户确认
4. 用户确认要点后，系统基于要点生成全新文章
5. 输出的文章结构、表达与原文完全不同
```

**场景 C：风格转换**
```
用户流程：
1. 粘贴公众号长文链接
2. 选择「换平台风格」意图
3. 获得适合小红书/抖音/微博的改写版本
```

## 五、详细功能规格

### F1: 五维度降重 Prompt

**触发条件**：intent === 'dedup' 或 intensity === 'heavy'

**行为**：
- 使用专用降重 system prompt（包含连续词打断硬约束）
- 五个维度全覆盖：句式重构、词汇革新、逻辑重排、人格注入、节奏打乱
- temperature 设为 0.7（比当前 0.85 更稳定）

**验收标准**：
- 使用文皮皮检测 5 篇改写文章，平均相似度 < 8%
- 改写后语义保留率 > 85%（人工评估）
- 不出现「胡说八道」或偏离原文事实的内容

### F2: 分段处理

**触发条件**：原文字数 > 2000

**行为**：
1. 按段落分割原文（保留段落间逻辑关系）
2. 每段独立送入 LLM 改写（附带上下文摘要）
3. 改写完成后拼接，做全文通顺性检查
4. 前端看到的仍然是连续的流式输出

**边界情况**：
- 单段超过 3000 字：按句子在 2000 字处切分
- 总字数超过 12000 字（当前 limit）：提示用户分批处理
- 段落间强关联（如：上段「首先」下段「其次」）：合并为一组处理

### F3: 连续词检测

**触发时机**：AI 改写完成后

**算法**：
- 使用滑动窗口（长度 8-20 字）
- 逐个窗口在改写结果中搜索与原文的完全匹配
- 输出：匹配片段列表（含位置、长度）

**性能要求**：
- 5000 字文章检测时间 < 200ms
- 不阻塞用户看到改写结果

### F4: 自动修补

**触发条件**：F3 检测到残留片段

**行为**：
- 提取残留片段 + 前后各 30 字上下文
- 针对这些片段调用 LLM 做局部改写
- 要求：替换后不能再有连续 5 字与原文相同
- 修补后替换回原位置

**限制**：
- 最多修补 10 处（超过说明整体改写质量差，应该重做）
- 单次修补不超过 100 字

### F5: Randomizer 集成

**触发条件**：intent === 'dedup'

**行为**：
- 在改写 + 修补完成后，调用 `randomizeText()` 做最终后处理
- 同义词替换 + 标点随机化 + 段落节奏打散 + 口语停顿词

### F6: 预估相似度展示

**计算方式**：
- 基于 F3 连续词检测的结果
- 公式：`1 - (totalMatchedChars / totalOriginalChars)` 的简化版本
- 加权：长匹配片段权重更高

**展示**：
- 结果面板顶部状态栏
- 颜色编码：绿色 < 5%，黄色 5-10%，红色 > 10%
- 附带小字提示：「仅为预估值，实际以查重平台结果为准」

### F7: 降重进度反馈

**展示**：
- 替代当前简单的「生成中」标记
- 显示当前阶段 + 进度条动画
- 阶段：`AI改写中 → 检测连续词 → 优化修补 → 完成`

### F8: L3 信息重组模式

**触发条件**：intensity === 'heavy'

**两步流程**：
1. Step 1：调用 LLM 提取原文 5-10 个核心要点（bullet points）
2. 前端展示要点列表，用户可编辑/删除
3. Step 2：基于用户确认的要点，调用 LLM 生成全新文章

**验收标准**：
- 信息保留率 > 80%
- 相似度 < 3%（因为骨架完全重建）
- 文章可读性评分 ≥ 8/10

## 六、验收标准汇总

| 项目 | 验收条件 |
|------|---------|
| 降重效果 | 5 篇测试文章，文皮皮相似度均 < 8%，平均 < 5% |
| 语义保留 | 改写后核心信息点无遗漏（人工逐条检查） |
| 可读性 | 改写后文章流畅自然，无病句、无逻辑断裂 |
| 性能 | 2000 字文章端到端 < 25s |
| 稳定性 | 连续 10 次改写无报错、无空输出 |
| UI 反馈 | 阶段进度清晰、相似度展示准确 |
| 专有名词 | 人名、地名、品牌名、数字保持不变 |

## 七、风险与缓解

| 风险 | 概率 | 缓解措施 |
|------|------|---------|
| LLM 不遵守连续词约束 | 中 | 后处理层做硬检测 + 自动修补 |
| 分段处理导致上下文断裂 | 低 | 每段附带上下文摘要 |
| 深度改写信息丢失 | 低 | 要点确认环节让用户把关 |
| 预估相似度与实际偏差大 | 中 | 标注「仅供参考」，不做绝对承诺 |
| 改写耗时超预期 | 低 | 分段并行 + 超时兜底 |
